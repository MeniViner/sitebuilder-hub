# דוח מוצר ועיצוב: Analytics Dashboard

תאריך: 2026-07-07  
יעד: `http://localhost:5177/#/analytics`  
סוג עבודה: ניתוח מעמיק + התחלת יישום

## תקציר

דף Analytics הנוכחי הוא כלי גרפים שימושי, אבל הוא עדיין לא מתפקד כמוצר Analytics. הוא נותן למשתמש לבחור מדד, קיבוץ ופילטרים, אך לא מוביל אותו אל החלטה: מה הבעיה הכי חשובה, מה היקף הפגיעה, מה מקור הנתון, מה כדאי לעשות עכשיו, ואיזה אתר לפתוח.

הפוטנציאל של הדף הוא להיות Control Center אנליטי לכל צי האתרים: מסך שמחבר בריאות, גרסאות, גיבויים, Jobs, הרשאות, נפחי אחסון ומעבר TXT/Mongo לתמונה אחת שמאפשרת סדר עדיפויות תפעולי.

## מה יש היום

הדף כולל:

- כותרת, תקציר תפעולי ו־ModeBoundary.
- חיפוש, פילטרים מתקדמים ותצוגות מהירות.
- ארבעה KPI בסיסיים.
- בונה גרפים כללי: קיבוץ, מדד, Top groups וסוג גרף.
- Heatmap של תקינות לפי סביבה.
- גרסאות נפוצות.
- Jobs לפי סטטוס.
- Top sites לפי המדד הנבחר.

כל אלה הם רכיבים נכונים, אבל כרגע הם מסודרים כארגז כלים ולא כזרימת עבודה.

## בעיות מוצריות מרכזיות

| אזור | בעיה | השפעה |
| --- | --- | --- |
| היררכיית מסך | הדבר הראשי הוא "דשבורד גרפים", לא "מה דורש טיפול" | המשתמש צריך לחשוב כמו אנליסט במקום לקבל סדר עדיפויות |
| KPI | המדדים הם סכומים גולמיים | אין ציון מצב, אין יחס, אין הקשר, אין שינוי ביחס למדיניות |
| תובנות | אין תור בעיות או המלצה ממוקדת | לא ברור מה לפתוח קודם |
| אמון בנתונים | אין סימון מקור נתון, freshness או גבול אמינות | Analytics עלול להיראות מדויק גם כשהנתונים חלקיים |
| פילטרים | הפילטרים חזקים אבל כבדים | הם מתאימים למשתמש מתקדם, לא לכניסה ראשונה למסך |
| גרפים | הגרפים כלליים מדי | הם עונים על "כמה יש בקבוצה" ולא על "מה מסוכן" |
| Layout | פאנלים משתמשים ב־`overflow: hidden`; אזורי טבלה/גרפים ארוכים אינם מוגבלים מספיק | תוכן עתידי עלול להיחתך, לדחוף את הדף או לשבור גלילה |
| Jobs | התפלגות Jobs מנותקת מאתרים ומבעיות | אין הבחנה בין כשל שמשפיע על Production לבין כשל היסטורי |
| Top sites | הרשימה מחוברת למדד אבל לא לסיבה | אין עמודת "למה האתר כאן" או פעולה מומלצת |

## הפוטנציאל המלא של הדף

הדף צריך לענות על חמש שאלות קבועות:

1. האם צי האתרים במצב טוב עכשיו?
2. מה שלושת הסיכונים החשובים ביותר?
3. אילו סגמנטים אחראים לרוב הסיכון: Production, יחידה, בעל אתר, גרסה, אחסון, TXT/Mongo?
4. אילו פעולות כבר רצות או נכשלו?
5. איפה פותחים את האתר הנכון כדי לטפל?

## מבנה מומלץ

| שכבה | מטרה | רכיבים |
| --- | --- | --- |
| Executive strip | מצב כללי תוך 10 שניות | ציון מצב, אתרים בסיכון, Production בסיכון, כשלי Jobs, אמון בנתונים |
| Insight queue | סדר עדיפויות | 4-6 תובנות לחיצות שמפעילות פילטר/קיבוץ מתאים |
| Decision map | חלוקה לתחומי אחריות | בריאות, גרסאות, Recovery, הרשאות, אחסון, Data backend |
| Investigation workbench | חקירה חופשית | בונה הגרפים הקיים, אבל כשלב שני |
| Evidence tables | פעולה | רשימת אתרים עם סיבה, סטטוס, מקור נתון וקישור לפתיחה |

## מטריקות שצריך לחשב

| מטריקה | נוסחה אפשרית | הערה |
| --- | --- | --- |
| Portfolio health score | 100 פחות נקודות סיכון לפי failed/warning/outdated/stale backup/job failed | Snapshot בלבד עד שיהיה endpoint היסטורי |
| Attention sites | סטטוס אתר, תקינות, גרסה, גיבוי או Admin sync בעייתיים | צריך לשקף גם Production |
| Recovery exposure | גיבוי חסר/ישן/נכשל, inventory לא עדכני, backup capability חסום | כיום יש רק חלק מהשדות בדף |
| Release drift | אתרים שאינם על latestKnownVersion או versionStatus != up_to_date | צריך להבדיל patch/minor/major בעתיד |
| Data maturity | יחס Mongo/TXT + backend reachability | חשוב במיוחד במעבר ל־Builder backend |
| Operational friction | Jobs failed/retrying/awaiting approval, לפי סוג וסביבה | צריך לחבר Job לאתר |

## פערי נתונים לשלב הבא

- חסר endpoint היסטורי ל־trend אמיתי.
- חסר summary מוכן ל־Analytics: כרגע הדף מחשב הכל בצד לקוח.
- חסר מיפוי Job -> site עם חומרת השפעה עסקית.
- חסר freshness מפורש לכל מקור נתון.
- חסר שדה "recommendedAction" או "nextBestAction" לכל אתר.

## יישום שמתחיל עכשיו

היישום הראשון צריך לשפר את המוצר בלי לשנות API:

- להוסיף Analytics Command Center מעל בונה הגרפים.
- לחשב ציון מצב ותובנות מהנתונים הקיימים.
- להציג Insight queue לחיץ שמפעיל פילטרים וקיבוצים קיימים.
- להוסיף Decision map שמראה תחומי סיכון והתקדמות.
- לשפר גלילה פנימית באזורי Top sites ו־Jobs.
- להשאיר את בונה הגרפים, אך למקם אותו ככלי חקירה ולא כמרכז החוויה.

## תוכנית דשבורדים פנימיים

הדף צריך להכיל סט דשבורדים פנימיים, לא מסך אחד ארוך בלבד:

| דשבורד | השאלה שהוא עונה | רכיבים נדרשים |
| --- | --- | --- |
| סקירה | האם הפורטפוליו במצב טוב ומה הכי דחוף? | Health score, Production risk, Evidence confidence, תור תובנות |
| תפעול | אילו תקלות ו־Jobs דורשים פעולה? | Failed/warning sites, Jobs failed/running, admin sync failures, health freshness |
| גרסאות | מי נמצא בפער גרסה ומה היקף הסיכון? | Version drift, currentVersion distribution, production outdated, release action |
| Recovery | איפה אין כיסוי התאוששות מספק? | Stale backups, failed backups, backup count/storage, freshness buckets |
| הרשאות | איפה יש עומס מנהלים או סנכרון כושל? | Admin-heavy sites, failed admin sync, owners/units, next owner view |
| קיבולת | איפה נפח/קבצים/Backend הופכים לסיכון? | Storage concentration, files count, TXT/Mongo split, large site drilldown |

היישום הבא באותו דף: tab switcher פנימי, כרטיסי מדד לכל דשבורד, וכרטיסי החלטה שמפעילים את הפילטרים והקיבוצים הקיימים.

## קריטריון הצלחה

משתמש שנכנס לדף צריך לדעת בתוך פחות מ־30 שניות:

- כמה אתרים דורשים טיפול.
- האם הבעיה קריטית ל־Production.
- האם הכאב המרכזי הוא גרסאות, גיבויים, Jobs, הרשאות או אחסון.
- באיזו תצוגה ללחוץ כדי להמשיך.
- אילו אתרים לפתוח ראשונים.
